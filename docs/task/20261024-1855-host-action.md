# 20261024-1855-host-action Let an engine ask its host to act, through the transcript

- **status**: pending
- **priority**: P1
- **owner**: (unassigned)
- **createdAt**: 2026-10-24 18:55

## Description

An engine sometimes has to act on the host that dispatched its task: comment,
change a status, file a follow-up. Today it can only do that by holding a host
credential and reaching the host over the network, which the engine sandbox is
built to prevent. Use the path the runner already has instead: the engine asks
the daemon through the local agent API (`20261024-1758-agent-local-api`), and
the daemon records the request as a transcript event on the caller's thread,
which reaches the host over the existing durable outbox. No host credential in
the engine, no network path to the host, no new frame. Requested by the bks
host (decision of 2026-10-24).

The runner stays generic: `method` and `params` are opaque to it; the host
defines and applies them, and writes the outcome on its side.

### Local agent API

- New method `thread.action {method: string, params?: object}` → `{seq}`.
  Run-scoped only (a token); operator connections get `forbidden`.
- The daemon appends one event to the token's thread, exactly like an engine
  event: next `seq`, enqueued in the outbox, delivered at least once:
  `thread_message {taskId, threadId, outboxId, data: {seq, kind: "host_action",
  input: {method, params}}}`.
- No reply from the host is awaited; the call returns once the event is
  enqueued. The host applies each event once, keyed by `(threadId, seq)`.
- CLI: `gino action <method> ['<json params>']`.

### Protocol (protocol.md §5, additive, stays v1)

- Add `host_action` to the recognized `thread_message.kind` set: an action the
  engine asked the host to take; `input` is `{method, params}`. A host that
  does not know it stores it opaquely, as for any kind.

### Isolation capabilities (same change)

- `capabilities` on register gains `sandbox` when a sandboxed launch is
  possible (bwrap probe passes, the daemon is not root) and `sandbox:allowlist`
  when `/dev/net/tun` is also available. `heartbeat.data` carries the same list
  as `capabilities`, so a host sees a change without re-enrollment.
- Document the host-delivered `engine.isolation` overlay as a host config field
  in protocol.md §3 (the agent already parses it; see
  `20261024-1341-host-isolation-overlay`).

### To verify while here

Task-scope provisioning entries (`project/…` symlinks into the store) resolve
inside the sandbox; only the global `CLAUDE.md` and `skills/` are known to be
bound.

Acceptance criteria: `gino action` from a sandboxed engine produces one
`host_action` event on the caller's thread and cannot target another thread;
the event survives a disconnect and is delivered on reconnect; capabilities
report `sandbox` only when a sandboxed run would start; task entries are
readable in a sandboxed run; agent gates and the docker e2e pass.
