# 20261024-1855-host-call Forward in-engine host calls over the agent socket

- **status**: pending
- **priority**: P1
- **owner**: (unassigned)
- **createdAt**: 2026-10-24 18:55

## Description

An engine sometimes has to act on the host that dispatched its task: read more
context, comment, change a status, file a follow-up. Today it can only do that
by holding a host credential and reaching the host over the network, which the
engine sandbox is built to prevent. Route those calls through the local agent
API instead (`20261024-1758-agent-local-api`): the engine asks the daemon, the
daemon forwards over its WebSocket, the host answers. The engine never holds a
host credential and needs no network path to the host.

The runner stays generic: method names and params are opaque to it; the host
defines them. Requested by the bks host (decision of 2026-10-24).

### Local agent API

- New method `host.call {method: string, params: object}` → `{result}` or an
  error. Run-scoped only (a token); operator connections get `forbidden`.
- The daemon stamps the call with the token's `{task_id, thread_id}`; the
  caller cannot name another task.
- Timeout 60 s by default; socket down or timeout → `unavailable`; a host error
  is passed through as `{code, message}` with `code` from the host.
- CLI: `gino host call <method> ['<json params>']`, printing the result JSON.

### Wire (protocol.md §5, additive, stays v1)

Live-only, like `fs_request` / `fs_response`: never persisted, acked or
replayed; correlated by a top-level `reqId` (a ULID minted by the runner).

| direction | type | envelope ids | data |
|---|---|---|---|
| agent → host | `host_request` | `reqId`, `taskId`, `threadId` | `{method, params}` |
| host → agent | `host_response` | `reqId` | `{ok: true, result}` or `{ok: false, error: {code, message}}` |

- The runner sends `host_request` only while connected; it fails pending calls
  with `unavailable` when the socket drops, and ignores a response for an
  unknown `reqId`.
- A host that does not implement the frame ignores it (§1); the call times out.
- Writes may be retried by the engine after `unavailable`; the host
  deduplicates by `reqId` (the CLI reuses its `reqId` on its own retries).

### Isolation capabilities (same change)

- `capabilities` on register gains `sandbox` when a sandboxed launch is
  possible (bwrap probe passes, the daemon is not root) and `sandbox:allowlist`
  when `/dev/net/tun` is also available. `heartbeat.data` carries the same list
  as `capabilities`, so a host sees a change without re-enrollment.
- Document the host-delivered `engine.isolation` overlay as a host config field
  in protocol.md §3 (the agent already parses it; see
  `20261024-1341-host-isolation-overlay`).

### To verify while here

Task-scope provisioning entries (`project/…` symlinks into the store) resolve
inside the sandbox; only the global `CLAUDE.md` and `skills/` are known to be
bound.

Acceptance criteria: `gino host call` round-trips through a host stub; a call
carries the caller's task and thread and cannot name another; a dropped socket
fails pending calls with `unavailable`; capabilities report `sandbox` only when
a sandboxed run would start; task entries are readable in a sandboxed run;
agent gates and the docker e2e pass.
